# Match Visuals: R15 Footballers, Ball Rework, Headshots, Lineup Board, Crowd Scale

Date: 2026-09-13
Status: approved by Marcel in chat ("implement all those and then the R15")

## Why

Marcel's playtest feedback on the current match presentation:

1. The ball hops from player to player (every pass is lofted), never sits at anyone's feet,
   passing looks aimless, and the ball is too big and floaty.
2. Footballers are primitive blocks. They should be normal Roblox-character size with real
   animations, and every footballer should look different (full avatar variety).
3. Each footballer needs a headshot, used on a FIFA/FM-style lineup board where players are
   dragged onto positions and swapped.
4. Fans are half the size of the player's character and stay in the stand after the match.

Nothing here touches the simulation layer (`MatchSim`, `Squad.assignScorers`, results, money).
All of it is presentation plus one small data addition (a per-player look seed).

## Scope split

Built in this order because each part depends on the previous one:

- **Part A: R15 footballers with randomized looks.** Replaces the block rig.
- **Part B: Ball and passing rework** in the presenter.
- **Part C: Crowd scale and clearing.** Independent, small.
- **Part D: Headshots and drag-and-drop lineup board** in the Club Office panel.

## Part A: R15 footballers

### Data: look seed

Every footballer gets a `look: number` seed.

- `Squad.makePlayer` assigns `look = rng:NextInteger(1, 2^30)` at generation. `Prospect`s
  generated by scouting get one the same way.
- `Profile.normalize` assigns a missing `look` to existing saved players as a stable hash of
  `id` and `name` (so old saves keep the same faces from now on, and warn-free).
- `Squad.MatchPlayer` (the timeline's home squad entries) carries `look` through.
- `TeamGen.generate` gives away players `look` from its own seeded RNG, so opponents look
  the same both times you meet them in a season.

### Shared `Appearance.luau` (pure)

`Appearance.fromSeed(seed: number): Look` derives a deterministic look table:

| Field | Source |
| --- | --- |
| `skin` | one of 8 skin tones |
| `heightScale`, `widthScale`, `depthScale`, `headScale` | small ranges around 1 (0.92 to 1.08 height, 0.9 to 1.1 width) |
| `hair` | catalog asset id from a curated list, or 0 for none (10% chance) |
| `face` | catalog face id from a curated list |
| `beard` | catalog face-accessory id or 0 (20% chance) |
| `headband` | catalog hat id or 0 (10% chance) |
| `boots` | one of 6 boot colours |

The curated id tables live in `Appearance.luau` and hold only Roblox-published catalog items
(free, script-free, loadable from any experience). Ids are verified in Studio during
implementation with `MarketplaceService:GetProductInfo`. Marcel can extend the tables later.

Implementation note (2026-09-13): the avatar catalog has no free Roblox-made beards, so
`beard` was dropped and replaced by a rare `shades` face accessory (4%). Headshots use a
classic mesh head with the face as a thumbnail decal, because the rig's dynamic head renders
untextured inside a ViewportFrame.

`Appearance.toDescription(look, kit, isKeeper): HumanoidDescription` fills a description:
body colours from `skin`, scales, `HairAccessory`, `Face`, `FaceAccessory`, `HatAccessory`.
Shirt/shorts/socks/boots are plain part colours applied after the rig exists (`applyKit`):
UpperTorso, arms and hands = shirt; LowerTorso and upper legs = shorts; lower legs = socks;
feet = boots; keeper uses the keeper kit with black shorts. Shirt number is a SurfaceGui on
UpperTorso front and back, as today.

### Client `Footballer.luau` (rewritten, same public interface)

Interface preserved so the presenter's movement code is unchanged: `new(parent, kit, number,
name, position, look)`, `setTarget`, `teleport`, `face`, `kick`, `celebrate`, `dive`,
`update(dt)`, `setTagVisible`, `destroy`, plus the read fields `position`, `yaw`, `speed`,
`busy`, `jitter`, `number`, `name`. The only signature change is the extra `look` argument.

Build: `Players:CreateHumanoidModelFromDescription(desc, R15)` on the client (verified to
work in Studio, 5.2 studs tall, 16 parts). The `Animate` script is removed. `HumanoidRootPart`
is anchored; all other parts hang off it through the rig's Motor6Ds and follow for free. Every
part is `CanCollide = false`, `CanQuery = false`, `CastShadow = false` (22 rigs on mobile).

Movement: `update(dt)` keeps the existing velocity model and writes one CFrame to the root
each frame (`position + (0, hipHeight, 0)`, yaw). Hip height is read from the Humanoid after
scaling so tall and short players both stand on the grass.

Animation: an `Animator` with Roblox-owned tracks. Idle `507766388`, walk `507777826`, run
`507767714`, celebrate picks randomly from cheer `507770677`, dance `507771019`, point
`507770453`. Track choice and speed follow the velocity magnitude (idle below 1.5, walk up to
`WALK_SPEED`, run above, `AdjustSpeed` proportional to speed so feet do not slide). Verified in
Studio: these tracks load and play on a client-built rig.

Kick and dive have no Roblox-owned animation, so they are procedural on top of the tracks:
a `RunService.Stepped` handler writes `Motor6D.Transform` for the right hip (kick swing over
0.4 s) and for both shoulders plus a root roll and drop (dive over 1.3 s). Verified in Studio:
a Transform written on Stepped survives the Animator for that frame.

Fallback: if rig creation throws (no network, description fetch failure) the module falls back
to the current block rig, which moves to `BlockFootballer.luau` untouched. A single warn per
match, never an error.

Load cost: 22 descriptions with catalog accessories are fetched during the walkout, which
already lasts several seconds. Rigs are created in `Presenter.new` in a spawned task per team,
and a footballer whose rig is still loading is skipped by `update` until it exists. The
timeline is unaffected.

## Part B: Ball and passing

All in `MatchPresenter.luau`. Numbers are TEMP and labelled as such in code.

- **Size.** Ball diameter 0.9 studs (a real ball is 0.6 at this scale; slightly larger for
  readability). Rests at `SURFACE_Y + 0.45`.
- **Rolling.** A ground pass moves in a straight line with ease-out deceleration and rotates
  around the axis perpendicular to its travel by `distance / radius` so it visibly rolls.
- **When it leaves the ground.** Passes under 45 studs roll. Longer passes (switches) and all
  shots are lofted with the existing arc. Only one arc family, no bouncing on landing.
- **At feet.** The holder keeps the ball 1.1 studs ahead of the right foot. While dribbling
  the ball is knocked 3 to 4 studs ahead every 0.6 s and the carrier runs onto it, so it
  alternates between "at feet" and "just ahead". Receiving a pass ends with a 0.15 s stop
  (the first touch) before the receiver becomes the holder.
- **Build-up play instead of random pinging.** Filler passes pick a receiver from the three
  nearest teammates (excluding the keeper) with a forward bias; 15% of the time the holder
  plays a long switch to the far-side midfielder or forward. Turnovers happen by
  interception: 20% of filler passes are intercepted by the opponent nearest the pass line,
  who becomes the holder. Sequences (`playSequence`) keep the DEF > MID > FWD chain but use
  the same ground/lofted rule.
- **Spin at feet.** While held or dribbled the ball rotates slowly to match the carrier's
  speed.

## Part C: Crowd

In `WorldBuilder.buildCrowd`:

- Seated fan proportions at character scale: body block 1.8 wide, 2.6 tall, 1.4 deep; head
  ball 1.2. Total about 3.8 studs seated against a 5-stud standing character.
- `FAN_SPACING` becomes 2.6 so wider fans do not overlap. The mobile budget stays 500 blocks;
  the density formula is unchanged.

In `MatchService`: when the phase returns to `Manage` the crowd folder is cleared. Fans exist
only from PreMatch to full time.

## Part D: Headshots and lineup board

### `Headshot.luau` (client)

`Headshot.render(parent: GuiObject, look: number, kit: Color3): ViewportFrame`. Builds a rig
from the look (same `Appearance` path as Part A) once per look seed, keeps only `Head` plus
the accessories attached to it, and drops it in a `ViewportFrame` with a camera framing the
face from slightly above. A `WorldModel` is not needed. Results are cached per look seed for
the session; a headshot whose rig is still loading shows the shirt number until ready.

### Lineup board (Club Office panel, Squad tab)

Replaces the row list for the starting XI with a pitch view. The bench and reserve rows stay
as a list below.

- A green pitch panel with the 4-4-2 slots from `Pitch.formationSlots` mapped to 2D, each
  slot a card: headshot, shirt number, surname, overall, role badge, injury marker.
- Bench and reserves render as cards in a horizontal strip under the pitch.
- **Drag and drop** with mouse and touch: press a card, drag a ghost copy, release over
  another card to swap. The drop fires the existing `swap` action with the two player ids;
  the server keeps all its rules (Auto Squad must be off, injured players cannot start). The
  existing tap-two-players swap is kept as the fallback for accessibility.
- With Auto Squad on, cards are shown but not draggable and the toggle explains why, as today.

Away squads never appear here, so the away look seeds only matter for the match.

## Testing

- Pure Luau tests (run through `tests/RunAll.luau`): `AppearanceTest` (same seed gives same
  look, values within range, all ids come from the curated tables), `SquadTest` and
  `TeamGenTest` extended for `look`, `ProfileTest` for the backfilled seed.
- Studio checks: a 30-second debug match from the office computer; observe walkout, running,
  a goal celebration, a keeper dive; console has no errors; screenshot the stand for fan
  scale; open the Squad tab, drag a bench player onto a starter, confirm the server swaps.
- Fallback check: force `CreateHumanoidModelFromDescription` to throw once in Studio and
  confirm the match still plays with block rigs.

## Out of scope

Real kit textures (uploaded clothing), goalkeeper gloves as separate assets, per-player
animation styles, layered clothing boots, and any change to how results are simulated.
